# 对话总结导出为 Markdown

把当前这场对话总结、整理成一份**规范的中文 Markdown 技术文档**并写入项目文件。目标是让文档本身可读、可跳转、可长期归档，而不是简单堆叠原始问答。

## 核心规则

- **全程使用简体中文**（遵循用户全局偏好），不要用日语/英语。
- **不要调用 `/export` 命令**去生成，那个产物不是规范 Markdown。直接用 Write 工具手写生成 `.md` 文件。
- **只保留有价值的内容**：技术讨论、结论、代码分析、方案对比、踩坑与解决。
- **主动剔除元对话**，包括但不限于：
  - 关于“导出文档”“生成/使用这个技能”本身的几轮对话；
  - 纯闲聊、确认、寒暄、“好的/继续”之类无信息量的往返；
  - 工具调用过程细节（除非结论本身依赖它）。
- 忠实原对话的技术结论，**不要杜撰**未讨论过的内容；如果中途有过更正（例如先给了错误方案后又纠正），以**最终正确结论**为准，并可保留“更正”这一事实作为提醒。
- **中文文案用中文标点，代码与英文文案用英文标点**。中文代码注释也算中文文案。详见下方「标点符号规范」。

## 文档结构（必须遵循）

按以下骨架组织，顺序不变：

1. **一级标题**：概括这次对话的主题（如 `# XXX 技术讨论`）。
2. **引言区**（标题下方，用 `>` 引用块）：一行主题说明 + 日期。日期用当前实际日期（绝对日期，如 `2026-08-04`），不要用“今天/昨天”。
3. **目录**：`## 目录`，有序列表，每项是**可点击的锚点链接**，指向下方对应章节。中文标题的 GitHub 锚点规则：转小写、去标点、空格转 `-`、中文字符保留。链接前先自检格式。
4. **正文分章节**：每个独立议题一个 `##` 章节，按对话推进的逻辑顺序排列。章节内部：
   - 用 `**结论：**` 或加粗句**先给结论**，再展开原因/推导；
   - 代码块**必须标注语言**（```swift / ```objc / ```text 等）；
   - 保留源码定位引用（如 `文件名.swift:123`），这类引用有价值；
   - 适合对比的内容用 **Markdown 表格**；
   - 需要区分层级/风险/优先级时用有序列表或加粗小标题。
5. **章节之间用 `---` 分隔线**。
6. **最后一节 `## 总体结论`**：用有序列表把全篇最关键的几条结论浓缩收尾。

## 标点符号规范

判断标准是**这段文字属于中文文案还是代码/英文**，而不是“在不在代码块里”。

**必须用中文标点的地方**（，：；（）""、——……）：

- 中文正文、列表项、表格里的中文单元格、中文标题；
- **中文代码注释**——注释是给人读的中文文案，和正文同等对待：

```swift
// 冷启动：URL 随场景一起送到
/// 只准备目录，很快。loadData 之前必须先调用
// 场景可能断开又重连，setup 会再跑一次，状态栏图标别重复创建
```

**必须保留英文标点的地方**（改了就是错的）：

| 场景 | 例子 | 原因 |
|---|---|---|
| 代码语法 | `replaceAnimation(with:fileExtension:)`、`completionBlock(item);` | 参数标签冒号、括号、分号是语法 |
| 行内代码内的一切 | 反引号 `` ` `` 包起来的内容 | 原样引用代码 |
| shell 语法 | `spctl --type exec "$M/App.app"` | 引号是 shell 语法 |
| 数字与格式 | 小数 `0.3` 秒、时间戳 `19:36:09.020`、版本号 | 句点/冒号是格式的一部分 |
| 英文原文引用 | 报错原文 `cannot open files in the "XXX" format` | 引述英文原文，连引号一起保留 |
| Markdown 语法 | 链接的 `](#锚点)`、表格的 `|` | 改了链接直接失效 |
| 纯英文句子 | 整句无中文的段落 | 本来就是英文文案 |

**实操做法**（手写时就按中文标点写，若要批量转换则遵循）：

1. 先把不能动的部分挖出来占位：代码块、行内代码、Markdown 链接的 `](...)`；
2. 判断语境时以“该行/该句是否含中文”为准，不要只看标点是否紧邻中文字符——`AppKit,UIKit`、`**加粗**:后面`、`)后面` 这几类都会漏；
3. **句点不要批量替换**：未被保护的英文句点几乎都是小数、文件名、API 名（`0.3`、`Info.plist`），转成句号就错了。中文句子结尾手写时直接用「。」；
4. 引号按内容判断：内含中文转中文引号，纯英文的大概率是原文引用，保留英文；
5. 转换后核对代码块内容与转换前**逐块一致**，确认没被误改。

## 文件命名与位置

- **默认写到项目根目录**（当前工作目录），除非用户指定了别的路径。
- 文件名用**能体现主题的中文短语** + `.md`，如 `lottie-抓帧技术讨论.md`。避免时间戳式的机器名，除非用户要求。
- 若同名文件已存在：先 Read 确认，再决定覆盖还是换名，不要盲目覆盖用户已有内容。

## 生成流程

1. 回看当前对话，识别出有价值的技术议题，按逻辑分组为若干章节。
2. 剔除元对话与无信息往返（见上）。
3. 按上面的结构骨架组织内容，先列目录锚点，再逐章写。
4. 用 Write 工具一次性写出 `.md` 文件。
5. 回复用户：告知文件绝对路径、格式要点（目录/章节/表格/代码块/结论）、以及已排除的内容范围；并主动提示可改文件名、位置或增删章节。

## 质量自检（写完前过一遍）

- 目录每个锚点都能对应到一个真实存在的 `##` 标题吗？
- 所有代码块都标了语言吗？
- 每个章节是否都先给了结论？
- 是否已剔除关于导出/技能/闲聊的元对话？
- 是否有 `## 总体结论` 收尾？
- 全文是否为简体中文？
- 中文文案（含中文代码注释）是否都用了中文标点？反过来，代码语法、shell 引号、小数、时间戳、Markdown 锚点、英文原文引用是否都保持了英文标点？

## 边界情况

- 若当前对话几乎没有可归档的技术内容（纯闲聊/纯操作），如实告知用户“本次对话缺少可整理的技术内容”，并询问是否仍要导出。
- 若用户明确指定了文件名、路径、要包含/排除的章节，以用户指定为准，覆盖上述默认。
- 若对话很长、议题很多，优先保证结论与方案完整，过程性推导可适当压缩，但不要丢失关键的“为什么”。
